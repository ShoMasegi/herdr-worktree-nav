# エラーハンドリング

失敗を何に変えてよいか、どの失敗をその変更で引き受けるべきか、そして失敗は画面のどこに出るか。

このページがあるのは、同じ欠陥が設計の後になってレビューで 1 件ずつ見つかり続けたからです。以下の規則はほとんど新しいものではなく、doc コメントや[各種の記録](../adr/)の中で既に適用されていました。書き出す目的は、プルリクエストごとに再発見し直すのをやめることです。

## ここでのエラーとは

これはピッカーです。自力で失敗しうる計算はほとんどありません。失敗のほぼすべては外の世界が言ったことです。git が拒否した、herdr が答えない、`gh` が入っていない、設定ファイルに不正な行がある。

つまりここでの失敗は、ほぼ常に**誰かが読む 1 文**であって、コードが分岐するための値ではありません。エラー型が `anyhow::Error` ひとつで、独自の enum が無いのはそのためです。variant ごとに振る舞いを選ぶ呼び出し元がいれば独自型は割に合いますが、そうした呼び出し元はいません。選ぶのは*言うか、言わないか*であり、このページの残りはその話です。

帰結が 2 つあります。

- **git と herdr 自身の言葉がメッセージです。** 言い換えません。どのコマンドを実行したかは adapter が付け、それより上はその言葉をそのまま上げます。`one_line` が 1 行しかない画面のために平坦化しますが、加工はそれだけです。
- **言葉は道中で失われてはいけません。** 捕まえて自前の散文に書き直された失敗は、トラブルシュートする人に必要な半分を落とします。git が話すロケールがただ 1 箇所で固定されているのも、`src/` が git をちょうど 1 つしか起動してよくないのも、そのためです。どちらも `scripts/check-invariants.sh` が守っています。

## 肝心の規則

> **失敗は、正当な答えも取りうる値になってはならない。**

要点はこれだけです。このページの他の規則はすべてこの帰結です。

見に行けなかった `git status` が返す `Ok(false)` は、クリーンな作業ツリーと区別がつきません。そして sweep はその値を根拠に削除します。壊れた `.git/config` に当たった `git remote get-url` の `Ok(None)` は、`origin` が無いリポジトリと区別がつきません。そしてユーザーは remote を見るよう言われます。起動できなかった `git` の `None` は、リポジトリの外にある pane と区別がつきません。そしてセッション全体が未分類として描かれ、理由はどこにも出ません。

必要になった場所では型が既にこの区別を持っており、真似すべき形はそこにあります。

- `WorkingTree` は `bool` ではなく `Clean | Dirty | Unreadable` です。「dirty でない」はチェックアウトを削除する根拠として誤りです。それは*まだ誰も訊いていない*と*git が答えなかった*も意味するからです。
- `Refs` は言葉を持つ `Read | Unreadable(String)` です。マーカーが無い行と、マーカーを読めなかった行は、行の上では同じに見えるからです。

**それでも潰さざるを得ないときは、何を飲み込んでいるかを書くこと。** 正しい潰しもあります。`gh` が無い・認証されていない・オフラインであることは意図的に空リストへ縮退させており、その理由が [ADR 0003](../adr/0003-git-first-gh-optional.md) です。欠陥との違いは使った演算子ではありません。**上のコメントが、そこへ届きうる失敗をすべて名指しし、そのいずれも正常な答えと区別しなくてよい理由を述べているか**です。

比べてください。こちらは正しく、そう書いてあります。

```rust
// A checkout git could not answer for gets no marker — no marker beats the wrong marker —
// but it is not recorded as clean, because that is a claim and this is the absence of one.
let dirty = git.is_dirty(checkout_path.as_str()).ok();
```

こちらは成り立たない同値を主張していて、issue #33 そのものです。

```rust
// A path that is not in a repository, and a git that failed, are the same thing here:
// the pane is simply not grouped.
let identity = git.identify(cwd).ok().flatten()?;
```

したがって、port の `Result` を素の値に変える箇所には、そこへ何が届きうるか・なぜ区別しなくてよいかを述べる `// swallows:` の行を付けます。その行が無い箇所は、判断ではなく見落としとして読みます。

## 4 つの分類と、それぞれの扱い

有用な問いは「どれくらい酷いか」ではありません。**その値が誤っていたとき、人やコードは何を結論するか**です。

### C1 — 誤った断定

失敗が「安全だ」「片付いた」と言う値になって届き、何かがそれに基づいて動く。削除が通る、マーカーが描かれる、誤った原因を名指しする文が出る。

**常に直し、目の前の変更をブロックします。** 交渉しない唯一の分類です。ユーザーが取り返せないものを失う唯一の分類だからです。

### C2 — 無言の縮退

失敗が「報告なし」として届く。偽は表示されず何も壊れませんが、ピッカーは主張より静かに少ない仕事をしており、画面のどこもそれを言いません。

**言葉を運んでプロンプト行に出すことで直します。** その配管こそが notice 機構の目的で、1 件足すのが設計ではなく 1 行で済むべきです。

### C3 — 報告の不備

失敗は検出され、報告もされている。文言・置き場所・言語・消えるタイミングが誤っている。

**変更をブロックしません。** issue に起票し、同類とまとめて直します。

### C4 — 受け入れる限界

正直な答えが「見ていません」である場合。`git status --porcelain` は ignore されたディレクトリ配下の作業を見られず、出力をどう読んでも変わりません。見るには別の問いを立てる必要があります。

**限界として書き出し、close します。** 後の読み手にとって重要なのは*誰も気づかなかった*と*見ないと決めた*の違いで、記録できるのは後者だけです。

## レビューでのトリアージ

レビューでエッジケースが見つかるのは正常であって、その変更の失敗ではありません。ラウンドを費やしているのは、毎回「これはこの PR の物か」を判断し直していることです。

> **指摘が目の前の PR をブロックするのは、次のいずれかのとき:**
>
> **(a)** C1 である、または
> **(b)** その変更が初めてそれを到達可能にした、あるいは初めて load-bearing にした。
>
> **それ以外は起票します。** 起票は「直さない」ではなく「**直すべき変更はこれではない**」です。

効くのは (b) です。欠陥が何年前からあっても、その変更の担当になりうる——[issue #56](https://github.com/ShoMasegi/herdr-worktree-nav/issues/56) は sweep が存在するよりずっと前から黙って捨てられていた `worktree.list` の失敗で、sweep の `Enter` が 2 回目の listing を初めて load-bearing にしたときにブロッキングになりました。

つまりレビュアーの仕事は**分類すること**であって、議論することではありません。分類と番号だけで、レビューコメントとして完全です。

直さずに起票する場合、issue にはどこで見つけたか、既存の欠陥かどうかを書きます。後の読み手が、先送りと見落としを区別できるようにするためです。

## 失敗は画面のどこに出るか

失敗がユーザーに届く場所は 3 つあり、違いは寿命です。

**状態 (condition)** は、何かが測り直すまで真であり続けるものです。git が refs を読めなかったリポジトリ、追いついていないリスト。これは**毎フレーム状態から導出**し、push も保存もしません。それが正しく引退する理由です——成り立たなくなったフレームではその文がそもそも produce されないので、取り下げを誰かが覚えておく必要がありません。

**出来事 (event)** は、ある瞬間に真だったものです。削除が拒否された、そのキーはここでは効かない。これは **push** し、それへの応答になりうる次の操作で引退します。

この 2 つを取り違えているのが [#64](https://github.com/ShoMasegi/herdr-worktree-nav/issues/64) と [#35](https://github.com/ShoMasegi/herdr-worktree-nav/issues/35) です。出来事として push された状態は、それが describe していたものより長生きします。placeholder として扱われた状態は、横に 60 桁空けたフィルタチップに行を奪われます。

**ブロッキングな失敗**が 3 つめで、これは種類が違います。ユーザーが頼んだ手順が失敗し、理由を読めるよう画面を保持するものです。これが無いとポップアップはプロセスの終了と同時に消え、成功したのと区別がつきません。

3 つに共通する規則が 2 つあります。

- **どの幅でも、失敗があるべき場所に空白を出してはいけません。** 文が入らない行は件数を出し、無を出しません。避けているのは、端末が狭かったせいで健康そうに見えるピッカーです。
- **`dump` が省略なしの写しです。** git が言ったことを 1 行が丸ごと持つことは原理的にできないので、バグ報告で実行を求めるサブコマンドがリポジトリごとに全文を出します。画面は要約、言葉があるのは `dump` です。

## panic

出荷されるコードは panic しません。release プロファイルは `panic = "abort"` なので、panic はユーザーが報告できるどこかに現れるのではなく、ピッカーをプロセスごと落とします。

`unwrap` と `expect` はテストとテスト用の fake のものです。`#[cfg(test)]` の外の `src/` で使うならコメントに理由が要り、その理由は「値が欠けえない理由」でなければなりません。「まず起きない」は理由になりません。

`join` が失敗しうる唯一のケースはスレッドが panic したときで、出荷されるバイナリでは上記の理由により到達不能です。`app::collect` はその腕を load-bearing に見せたままにせず、そのことを書き記しています。
