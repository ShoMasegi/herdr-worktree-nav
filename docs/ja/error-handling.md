# エラーハンドリング

プラグインを使う上で何が失敗しうるか、それぞれの失敗を何に変えてよいか、そしてそれが画面のどこ
に出るか。

## 失敗はどこから来るか

ピッカーが自力で失敗しうる計算はほとんどありません。うまくいかないことのほぼすべては外の世界が
言ったことであり、外の世界は 4 つしかありません。

- **herdr**（ソケット越し）。セッションそのもの（pane・タブ・ワークスペース・worktree）と、それ
  に対するあらゆる操作。
- **git**（子プロセス）。リポジトリの同定、refs、作業ツリー、fetch、削除。
- **`gh`**（子プロセス）。どのプルリクエストが取り込まれたか。それだけ。
- **プラグインの設定ファイル**。

5 つ目として端末がありますが、性質が違います。端末が失敗することはなく、失敗の何割をユーザーが
読めるかを決めるだけです。端末の規則はこのページの終わりにあります。

つまりここでの失敗は、ほぼ常に**誰かが読む 1 文**であって、コードが分岐するための値ではありませ
ん。エラー型が `anyhow::Error` ひとつで、独自の enum が無いのはそのためです。variant ごとに振る
舞いを選ぶ呼び出し元がいれば独自型は割に合いますが、そうした呼び出し元はいません。選ぶのは*言う
か、言わないか*であり、このページの残りはその話です。

帰結が 2 つあります。

- **git と herdr 自身の言葉がメッセージです。** 言い換えません。どのコマンドを実行したかは
  adapter が付け、それより上はその言葉をそのまま上げます。`one_line` が 1 行しかない画面のために
  平坦化しますが、加工はそれだけです。
- **言葉は道中で失われてはいけません。** 捕まえて自前の散文に書き直された失敗は、トラブルシュー
  トする人に必要な半分を落とします。git が話すロケールがただ 1 箇所で固定されているのも、`src/`
  が git をちょうど 1 つしか起動してよくないのも、そのためです。どちらも
  `scripts/check-invariants.sh` が守っています。

## 失敗の 5 分類

以下の分類は「どのツールが失敗したか」で切っていません。同じコマンドの同じ拒否でも、その後にユー
ザーの世界に何が残るかによって属する分類が変わります。そして訊く価値のある問いはそれだけです。
**これが起きた後、ユーザーの手元には何が残っているか。**

### 1. プラグインが続けられない

描くに値するものが何も残りません。ソケットのパスが環境に無い、最初のスナップショットがついに来
ない、ピッカーがそれ無しでは進めない操作が足元で失敗した。言う場所としての画面はありません。画面
自体が無いからです。

**扱い:** 失敗は `main` まで上がり、そこで stderr に出力され `ExitCode::FAILURE` で終了します。
herdr がそれを `herdr plugin log list` に残し、トラブルシューティングのページはそこへ人を送りま
す。

**規則:** この経路は、描くものが何も残らない失敗のためのものです。一覧とマーカー 1 つ減った表示
をまだ出せるピッカーは、この経路を通りません。それは分類 3 です。

### 2. ユーザーが頼んだことが起きなかった

キーが押され、操作が試みられ、失敗したか拒否された。頼んだのはユーザーであり、画面上の他の何も
それを言わない以上、説明はユーザーに対する借りです。ピッカー自体は無事です。

**扱い:** 1 文を、ユーザーがまだ見ている場所に出します。場所は 3 つあります。

- **ピッカーが出ている場合。** 文はプロンプト行に push され、次のキーが取り消します。ある瞬間の
  説明は、それへの返答になりえた次の操作で退場します。
- **ピッカーが進捗表示に変わっている場合。** ブランチを開くのは fetch とチェックアウトで数秒かか
  り、ポップアップはプロセスと一緒に消えます。そのため、そこでの失敗は画面を保持します。
  `Activity::Failed` が失敗した `Stage` と言葉を保持し、*読んだ*という意味のキーだけがピッカーを
  閉じます。保持しなければ、失敗と成功は見分けがつきません。どちらでもポップアップは消えるだけだ
  からです。
- **操作がピッカーより長く生きる場合。** 削除は自分専用のセッションで走るため
  （[ADR 0014](../adr/0014-removing-outlives-the-picker.md)）、書き込む窓はもう残っておらず、答え
  は herdr の通知として返ります。拒否は git 自身の言葉を運びます。何が失われるところだったかを言
  うのはその言葉だからです。そして通知のうち音を鳴らす唯一のものです。もう見ていない人に届かなけ
  ればならないからです。

この分類の多くは欠陥ですらありません。`RemovalOutcome::Refused` はたいてい git が仕事をしている
だけで（コミットしていない変更のあるチェックアウトを守るのが `git worktree remove` の役目です）、
`RemovalOutcome::BranchKept` はどこにもマージされていないブランチです。どちらも本物の失敗と同じ扱
いをします。プロンプト行から見れば、その違いはユーザーが付けるものであって、こちらが代わりに付け
られるものではないからです。

### 3. ピッカーは動いているが、名乗るほど知らない

ユーザーがしたことは何も失敗していません。失敗したのは行の裏側の読み取りです。ツリーを読み直せな
かった、あるリポジトリの refs を列挙できなかった、sweep 中に `gh` が拒否した。一覧は画面に残った
ままで、権威ありげに見えたままで、古いか欠けています。

**扱い:** **コンディション**。次に測り直されるまで真であり続ける文で、それが成り立つ間ずっとプロ
ンプトの脇に出ます。

肝心なのは寿命で、コンディションがメッセージでないのはそのためです。コンディションは
`notice::conditions` が**毎フレーム状態から導出**します。push されることも、文として保存されるこ
ともありません。もう間違っていないフレームはその文を単に生成せず、したがって取り消しを覚えておく
必要がどこにもありません。コンディションはキーが押されたときではなく、読み取りが成功したときに退
場します。キーを押しても古い一覧は新しくならないからです。

コンディションは*唯一の*痕跡でもありません。対象となった行は、得ていないマーカーを持ちません。そ
れが分類 4 です。

### 4. 外のツールは答えたが、その答えを信用できない

git は起動して戻ってきたが、見に行けなかった。読めない作業ツリー、列挙できない refs。保存すべき値
は*あり*、そして取りうる普通の値はどれも嘘です。

**扱い:** 専用の状態。「分からない」が答えとして読まれないようにします。`WorkingTree` は `bool`
ではなく `Clean | Dirty | Unreadable` です。`Refs` は言葉を持つ `Read | Unreadable(String)` です。
行はマーカーを描きません（マーカー無しは誤ったマーカーに勝ります）。そして、そのフレームが文を
出せる場合は、マーカーが無い理由をコンディション（分類 3）が言います。到達しうる失敗がそれを出
さない場合でも状態は運び、行が黙っている理由は状態の定義のそばに書きます。

間違えたときの代償が最も大きいのがこの分類です。壊れているように見えないからです。次の節の規則
は、この分類のためにあります。

### 5. こちらが選んだ縮退

任意の依存が無い・認証されていない・オフライン・遅い、といったときに、何も失敗させずに、宣言済み
の既定値で進みます。

- **`gh`** は取り込み済みプルリクエストの空リストに縮退します。理由は
  [ADR 0003](../adr/0003-git-first-gh-optional.md) の通りで、あの層は装飾であり、ピッカーを失敗さ
  せてはいけません。加えて制限時間（`GH_BUDGET`）を与えてあります。答えない `gh` は sweep をいつ
  までも開いたままにしてしまい、答えを得られない sweep とは、そう言わずに縮退した sweep だからで
  す。
- **設定ファイル**は、読めないか解析できないときに既定値へ縮退し、その際にプロンプト行で自分の名
  を名乗ります。キー 1 つの打ち間違いがピッカーを落としてはいけません。

**これを言い訳ではなく分類にしているもの:** 既定値がここか記録に書かれていること、*かつ*それを採
ったことをピッカーが声に出して言うことです。誰にも告げない縮退は、誰も見ていない分類 3 です。ど
こにも書かれていない縮退は、まだ気づかれていない事故です。

## エッジケースが帰着する規則

> **失敗は、正当な答えも取りうる値になってはならない。**

議論になるエッジケースはすべてこの規則の実例であり、議論ではなく規則を当てれば止まります。

見に行けなかった `git status` が返す `Ok(false)` は、クリーンな作業ツリーと区別がつきません。そし
て sweep はその値を根拠に削除します。壊れた `.git/config` に当たった `git remote get-url` の
`Ok(None)` は、`origin` が無いリポジトリと区別がつきません。そしてユーザーは remote を見るよう言
われます。起動できなかった `git` の `None` は、リポジトリの外にある pane と区別がつきません。そし
て git に訊いた pane がすべて未分類として描かれ、理由はどこにも出ません。

3 つとも同じ欠陥が 3 箇所に出たものです。分類 4 の失敗が普通の答えの形へ潰され、そうなった後は下
流でどれだけ気をつけてもその区別は戻りません。

### それでも潰すときは、何を飲み込んでいるかを書く

正しい潰しもあります。分類 5 は意図的な潰しです。欠陥との違いは使った演算子ではありません。**上の
コメントが、そこへ届きうる失敗をすべて名指しし、そのいずれも正常な答えと区別しなくてよい理由を述
べているか**です。

こちらは正しく、そう書いてあります。

```rust
// A checkout git could not answer for gets no marker — no marker beats the wrong marker —
// but it is not recorded as clean, because that is a claim and this is the absence of one.
let dirty = git.is_dirty(checkout_path.as_str()).ok();
```

こちらは成り立たない同値を主張していたもので、
[issue #33](https://github.com/ShoMasegi/herdr-worktree-nav/issues/33) そのものでした。失敗を
名指しする代わりに、コメントで失敗を言いくるめている形です。

```rust
// A path that is not in a repository, and a git that failed, are the same thing here:
// the pane is simply not grouped.
let identity = git.identify(cwd).ok().flatten()?;
```

いまの `app::collect::identify_one` は `Result<Option<PanePlacement>, String>` を返すので、
2 つは区別されます。答えなかった git は条件の 1 つになり、単にリポジトリの外にある pane は条件に
なりません。

したがって、port の `Result` を素の値に変える箇所には、そこへ何が届きうるか・なぜ区別しなくてよ
いかを述べる `// swallows:` の行を付けます。その行が無い箇所は、判断ではなく見落としとして読みま
す。

### どの指摘をその変更で引き受けるか

レビューでエッジケースが見つかるのは普通のことで、その変更の失敗ではありません。ラウンドを食う
のは、毎回「これはこの PR のものか」を決め直すことです。

> **次のどちらかのとき、指摘は目の前の PR をブロックします。**
>
> **(a)** 失敗が、何かがそれに基づいて動く値になっている（削除が通る、マーカーが描かれる、誤った
> 原因を名指しする文が出る）。
> **(b)** その変更こそが、それを到達可能にした、あるいは初めて効くようにした。
>
> **それ以外は issue にします。** issue にするのは「直さない」ではなく「直すべき変更はこれではな
> い」です。

(a) は交渉しない唯一の分類です。ユーザーが取り返せないものを失う唯一の分類だからです。(b) は実務
を担う条項です。欠陥は何年前のものでも、その変更の担当になりえます。
[issue #56](https://github.com/ShoMasegi/herdr-worktree-nav/issues/56) は sweep が存在するよりずっ
と前から黙って捨てられていた `worktree.list` の失敗ですが、sweep の `Enter` が 2 回目の一覧取得を
効くようにした時点でブロッキングになりました。

直さずに issue にするものは次の 3 つのいずれかで、issue にはどれかを書きます。偽りは表示しないが
名乗るほどの仕事をしていないことを画面のどこも認めない**黙った縮退**。失敗を捉えて言ってはいる
が、文言・位置・言語・消えるタイミングが誤っている**報告の欠陥**。そして、見に行かないのが正直な
答えである**受け入れる限界**（`git status --porcelain` は ignore されたディレクトリの下の作業を見
られず、見るには別の問いを立てるしかありません。[issue #68](https://github.com/ShoMasegi/herdr-worktree-nav/issues/68)）。閉じてよいのは 3 つ目だけです。後の読み手に必要
な区別は*誰も気づかなかった*と*そうしないと決めた*の間にあり、記録できるのは後者だけです。

## もう一度訊くこと

自然に直る失敗と決して直らない失敗は扱いが違い、その違いは「それが誰のものか」です。

- **`r` はすべてを読み直し**、`gh` が言ったことも忘れます。ピッカーが出ている間にプルリクエストが
  取り込まれうるからです。
- **sweep に入るとツリーを読み直し、前回 `gh` が拒否したところを訊き直します**
  （`Settled::forget_failures`）。`gh` の拒否はたいていネットワークかトークンの話で、`Shift-S` と
  次の `Shift-S` の間に直るからです。`gh` が返した答えは保持します。それは sweep を広げるだけだか
  らです。
- **外で何も変わらない失敗は、訊き直す価値がありません。** 解析できない `.git/config` は毎回同じ
  答えを返します。[issue #69](https://github.com/ShoMasegi/herdr-worktree-nav/issues/69) はこの区
  別がまだ引かれていないことです。

自動で再試行するものはありません。ユーザーが頼んでいない再試行は、たいてい決定的な失敗にプロセス
を 1 つ費やし、しかもその間それを隠します。

## スレッドから返る失敗

ピッカーの中ではなく横で走るものが 3 つあります。各チェックアウトが dirty かを訊く walk、sweep の
裏の `gh` 問い合わせ、そして自分のプロセスで走る削除です。3 つとも、開始したフレームが消えた後に
失敗しうるので、どれもループを止める形で失敗を返してはいけません。

いずれも成功と同じ経路で報告します。チェックアウトごと、リポジトリごと、削除ごとに 1 つの答えを返
し、失敗はその答えの中の値で、分類 4 か分類 5 です。*これは clean だ*と言うのと同じ channel で
*これは失敗した*と言えないスレッドは、失敗をログ以外のどこにも置けません。黙るのはそうしてです。

## 画面が失敗に対して負うもの

- **どの幅でも、失敗があるはずの場所を空白にしてはいけません。** 文に足りない行は数を出し、決して
  何も出さないことはありません。避けたい失敗の形は、端末が小さかったせいで健康そうに見えるピッ
  カーです。コンディションとプロンプト行が同じ桁を取り合わないのも同じ理由で、
  [#35](https://github.com/ShoMasegi/herdr-worktree-nav/issues/35) は、隣に十分な余裕があるフィル
  ターのチップにコンディションが行を奪われていたことでした。
- **幅が切り落としたものは、ユーザーが今いる場所で読めなければなりません。** `!` が一覧の上にパ
  ネルを開き、コンディションを全部そのまま載せます。数は*何かがおかしい*と言うには足りますが、対
  処するには足りません。そして、文を読むためにピッカーを閉じて別のコマンドを打たされる人は、結局
  読みません。パネルは行と同じように縮退します（入らない分は残りの数になります）。読むだけのもの
  だからで、切られた質問が別の質問になるのとは違い、切られた文は別の文にはならないからです。
- **導出すべきものを push しないこと。** メッセージとして保存されたコンディションは、それが記述し
  ていた対象より長く生き残ります。[#64](https://github.com/ShoMasegi/herdr-worktree-nav/issues/64)
  はまさにそれで、直し方は取り消す場所を用意することではなく分類 3 の形にすることです。
- **`dump` は省略なしの写しです。** git が言ったことの全文は 1 行には決して入らないので、バグ報告
  が求めるサブコマンドはリポジトリごとにすべての失敗を丸ごと出力します。画面は要約であり、言葉が
  あるのは `dump` です。

## 外を呼ぶコードを足すとき

新しい port のメソッド、あるいはその新しい呼び出し元は、レビューに出せるようになる前に 5 つの問い
に答えます。

1. 失敗したとき、5 分類のどれになるか。「失敗しない」が答えなら、それは port を通っているのだか
   ら、失敗しえます。
2. 呼び出し元はその失敗をどうするか。保持するか、push するか、導出するか、専用の状態を持つか。
3. `Result` を潰すなら、`// swallows:` の行は何か。
4. これによって下流に、普通の答えと区別できない値が生まれないか。
5. その失敗は訊き直す必要があるか。訊き直したとして、自然に直るものか。

## パニック

出荷されるコードはパニックしません。リリースプロファイルは `panic = "abort"` なので、パニックは
ユーザーが報告できるどこかに現れるのではなく、プロセスごとピッカーを落とします。

`unwrap` と `expect` はテストとテスト用フェイクのものです。`#[cfg(test)]` の外の `src/` で使うな
ら、コメントに理由が要ります。その理由は「値が欠けえない理由」でなければならず、「まず起きない」
は理由になりません。

パニックしたスレッドは `join` が失敗しうる唯一の場合で、出荷されるバイナリでは上記の理由により到
達しません。`app::collect` はその腕を効いているように見せておくのではなく、そのことを書いていま
す。
